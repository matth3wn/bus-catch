# T02: Deploy to Vercel and verify production

**Created GitHub repo (matth3wn/bus-catch), deployed to Vercel at https://bus-mu-ebon.vercel.app, verified page loads, manifest serves, API routes return data, and service worker registers.**

## What Happened

1. Installed `gh` CLI (via Homebrew) and `vercel` CLI (via npm global).
2. Authenticated with GitHub via `gh auth login` device flow (logged in as matth3wn).
3. Created public GitHub repo `matth3wn/bus-catch` with `gh repo create --public --source=. --remote=origin --push`. Pushed both `gsd/M001/S04` and `main` branches.
4. Authenticated with Vercel via `vercel login` device flow.
5. Deployed with `vercel --yes --prod`. Vercel auto-detected Next.js, built successfully (7 routes, 2 dynamic API routes, static manifest), and deployed to `https://bus-mu-ebon.vercel.app`.
6. No `SWIFTLY_API_KEY` configured — the app falls back to Metro API v2 + schedule mock data as designed.
7. Verified all 6 must-haves via curl + browser assertions.

## Deviations

- Needed to install `gh` and `vercel` CLIs (not pre-installed). Added ~3 min overhead.
- GitHub push required `gh auth setup-git` for credential helper after initial token auth had issues with plain `git push`.
- API routes return `source: "mock"` (schedule fallback) rather than live Metro API v2 data. This is expected behavior when the Metro GTFS-RT feed has no active trips at this time of day. The fallback chain is working correctly.

## Known Issues

- No `SWIFTLY_API_KEY` env var configured on Vercel — app uses Metro API v2 + schedule fallback only. Can be added later via Vercel dashboard for real-time Swiftly data.
